# 飞盘 HAT 赛事组织助手

微信小程序。参与者自助报名填报信息，组织者按**水平 + 性别**均衡地随机分队，
支持「必须同队 / 必须拆开」约束和手动微调；赛后录入战绩，积分自动计算。

一个活动里可以开多场赛事，每场按当次到场的人重新分队，积分在活动层汇总。

| 配置 | 位置 | 当前值 |
| --- | --- | --- |
| 小程序 AppID | `project.config.json` 的 `appid` | `wx7cffdec065873492` |
| 云开发环境 ID | `miniprogram/config.js` 的 `ENV_ID` | `cloud1-d2gsqw6y62291250e` |
| 管理员 openid | `cloudfunctions/*/lib/roles.js` | 已预填 1 个 |

换小程序或换环境时才需要改前两项。环境 ID 要用**开发者工具内**云开发控制台显示的那个，
而且必须显式写死——`wx.cloud.init` 不传 `env` 会连到"默认环境"，多环境时很容易连错。

> 云开发**不支持测试号**，必须用正式注册的小程序 AppID。

新环境从零搭起来需要两步：

### 1. 建数据库集合

云开发控制台 → 数据库，建这 7 个集合（名字一字不差）：

```text
events  signups  tournaments  divisions  matches  constraints  roles
```

**权限**：每个集合 →「权限设置」→ 自定义安全规则。`events` 填 `{"read": true, "write": false}`，
其余 6 个都填 `{"read": false, "write": false}`（只许云函数读写，原因见
[`数据库安全规则.md`](数据库安全规则.md)）。

**索引**：选中集合 →「索引管理」→ 新建。联合索引按表中顺序添加字段：

| 集合 | 字段（都选升序，除非注明） | 唯一 | 用途 | 优先级 |
| --- | --- | --- | --- | --- |
| `signups` | `eventId` + `openid` | **勾选** | 防止同一人重复报名 | **必须** |
| `signups` | `eventId` + `status` | | 活动报名名单 | 建议 |
| `signups` | `openid` + `status` | | 「我的报名」 | 建议 |
| `signups` | `eventId` + `isTest` | | 清理测试数据 | 可选 |
| `events` | `startTime`（降序） | | 活动列表排序 | 建议 |
| `events` | `ownerOpenid` | | 「我创建的活动」 | 建议 |
| `tournaments` | `eventId` + `createTime` | | 活动下的赛事列表 | 建议 |
| `divisions` | `tournamentId` + `version` | | 读取最新分队 | 建议 |
| `divisions` | `eventId` + `published` | | 积分榜判断是否已发布 | 建议 |
| `matches` | `tournamentId` + `createTime` | | 赛事下的比赛列表 | 建议 |
| `matches` | `eventId` | | 积分榜按活动汇总 | 建议 |
| `constraints` | `eventId` | | 分队约束 | 可选 |
| `roles` | `openid` + `role` | | 判断是否记分员 | 可选 |

**第一行那个唯一索引不能省**，否则用户连点提交会重复报名、白占名额。其余人少时可以先不建，
但数据积累多了查询会变慢甚至超时。

### 2. 部署 5 个云函数

右键 `cloudfunctions/` 下的每个目录，选
**「上传并部署：云端安装依赖（不上传 node_modules）」**：

```text
hat-event  hat-signup  hat-team  hat-match  hat-admin
```

`package.json` 里 `wx-server-sdk` 锁在 `~4.0.2`。云端在线安装有可能装到与 Node 版本
不兼容的新版本，所以不要改成 `*` 或 `latest`。

## 集合与索引是什么

**集合**相当于一张表，一类数据放一个集合。每条记录叫一个"文档"，集合之间用 id 互相引用
（比如报名记录里的 `eventId` 指向某个活动）。

| 集合 | 存什么 |
| --- | --- |
| `events` | 活动：时间、地点、人数上限 |
| `signups` | 报名：谁报了哪个活动、性别、自评水平、手机号 |
| `tournaments` | 赛事：某活动下的第几场、谁到场了 |
| `divisions` | 分队结果，每次分队存一个版本 |
| `matches` | 比赛：比分、谁上场、MVP |
| `constraints` | 分队约束：谁和谁必须同队/拆开 |
| `roles` | 记分员名单 |

**索引**相当于书的目录，让数据库按某个字段查得快，不用逐行翻。人少时没索引也能跑，
但记录越积越多后查询会变慢甚至超时（云数据库超时最常见的原因就是缺索引）。

勾了「唯一」的索引还会**拒绝写入重复的值**，在数据库层面挡住重复报名，
不依赖云函数里的检查有没有漏。

## 使用流程

**组织者**：创建活动 → 分享到群 → 报名截止后在管理台调整水平、设约束 → 关闭报名 →
新建一场赛事、勾选到场的人 → 分队 → 发布 → 每打完一场录一次战绩。
人员变动了可以再开一场赛事重新分队。

**参与者**：打开活动 → 填姓名、性别、水平自评、手机号（选填）→ 报名 →
分队发布后在赛事里看到自己在哪队 → 随时查积分榜。

**记分员**：打开赛事 → 比赛记录 → 录比分、勾上场名单、选 MVP。

## 用户角色

| 角色 | 怎么认定 | 能做什么 |
| --- | --- | --- |
| 参与者 | 默认 | 报名、查看积分榜与战绩 |
| 记分员 | `roles` 集合，管理员指定 | 录入/修改/删除比赛战绩 |
| 组织者 | 活动的创建者 | 建活动与赛事、管理报名、调整水平、分队、发布 |
| 管理员 | 云函数里写死的 openid 白名单 | 管理记分员，并拥有全部组织者权限 |

管理员可以操作任何人创建的活动。记分员能录战绩，但不能建赛事、不能分队、不能看或改水平。

### 查看自己的身份

打开「我的」页：

- 管理员：顶部显示「后台管理」卡片
- 记分员：顶部显示「记分员」卡片
- 组织者：在自己创建的活动详情页底部有「管理台」按钮

### 指定记分员（在小程序里操作）

用管理员账号进「我的」→「后台管理」，列表里是所有报过名的人，点某人即可切换记分员身份。

- **只有报过名的人才会出现在列表里**，想让某人当记分员，先让他随便报一场活动
- 对方要重新进一次「我的」页才会看到身份变化

### 增删管理员（要改代码）

管理员名单写在云函数里，而不是前端 `config.js`——前端是客户端代码，改一行就能冒充管理员。
权限一律在云函数里判定，前端的身份信息只用来决定按钮显不显示。

1. 拿到对方的 openid：让他报名任意活动，再到「后台管理」列表或云开发控制台
   `signups` 集合里找他那条记录的 `openid` 字段
2. 把 openid 加进 `ADMIN_OPENIDS`。**5 个云函数里各有一份**，全部都要改：

   ```text
   cloudfunctions/hat-admin/lib/roles.js
   cloudfunctions/hat-event/lib/roles.js
   cloudfunctions/hat-match/lib/roles.js
   cloudfunctions/hat-signup/lib/roles.js
   cloudfunctions/hat-team/lib/roles.js
   ```

3. 双击 `run-tests.cmd`。漏改了某一份会报"roles.js 副本不一致"
4. 5 个云函数全部重新部署

之所以有 5 份副本，是因为云函数各自独立部署，没法跨目录共享代码。漏改一份的后果很隐蔽：
这个人在某些功能里是管理员、在另一些里不是，表现为"有的按钮能点，有的点了报没权限"。

## 层级结构

```text
活动 event          报名在这一层
 └── 赛事 tournament  各自记录到场名单、各自随机分队
      └── 分队 division
           └── 比赛 match  记录比分、谁上场、MVP
```

两个层次的"参与"不要混淆：

- **到场**（赛事级）：这场赛事谁来了，决定分队范围
- **上场**（比赛级）：某一场比赛谁实际打了，决定得分

分队约束挂在**活动**层（"这两个人别同队"对每场赛事都适用，不用重设）。某场赛事有人没到时，
分队前会自动把缺席的人从约束里摘掉，剩不足 2 人的整条忽略，页面上会提示忽略了几条。

## 积分规则

| 情况 | 积分 |
| --- | --- |
| 所在队伍**获胜** | +3 |
| 所在队伍**落败** | +1 |
| 当选**本场 MVP** | 额外 +1 |
| **未上场** | 不计分 |

- MVP 由**胜方从败方的上场队员中选出 2 名**（单向，胜方队员拿不到 MVP 分），可以先不选、之后补录
- **不允许平局**，比分相同时录入直接报错
- 积分榜是**活动级汇总**：把该活动下所有赛事的得分按人合并，不跨活动累计

两个实现上的决定：

**积分不入库，每次由比赛记录实时推导**（`cloudfunctions/hat-match/lib/score.js`）。
存一份积分字段就一定会漂移——改一次比分、删一场比赛、换一次 MVP，存量数字就对不上了。
分值是文件顶部的三个常量（`WIN` / `LOSS` / `MVP_BONUS`），要调改一行。

**录入比赛后，该赛事禁止重新分队、禁止改到场名单。** 比赛记录引用的是队伍序号和队员 id，
重新分队会让引用全部失效。要重分得先删掉这场赛事的比赛记录。

## 球员水平不公开

参与者**只能看到自己的自评**，看不到组织者调整后的值，也看不到任何别人的水平。
队均水平和高分人数同样只对组织者和管理员可见。记分员也看不到，他只需要名字。

实现上在**云函数出口剥离**，不是靠前端不渲染——前端不渲染，数据照样发到了客户端，
在调试工具里一看就有。测试里用 `JSON.stringify` 全文断言参与者拿到的返回不含任何 `level` 字段。

## 修改代码后怎么生效

**前端和云函数的生效方式完全不同**，这是最容易踩的坑：

| 改动 | 生效方式 | 线上用户何时看到 |
| --- | --- | --- |
| `miniprogram/` 下任何文件 | 保存后开发者工具自动重编译 | 上传 → 提审 → 发布之后 |
| `cloudfunctions/` 下任何文件 | **必须右键重新上传部署** | **部署后几秒，不经审核** |
| 数据库数据、权限、索引 | 在控制台改 | 立即（权限规则有 1~3 分钟延迟） |

两个后果：

- **云函数改了不部署，不会报任何错**，只是改动静默不生效
- **云函数没有审核兜底**。开发版、体验版、正式版共用同一个云环境，部署一个有 bug 的
  云函数就是线上事故

### 建议的修改流程

1. 改动前 `git status` 确认工作区干净
2. 改代码
3. 双击 `run-tests.cmd`，确认全部通过
4. 改了云函数：先右键「开启云函数本地调试」验证，**线上用户此时仍跑云端旧版本**；
   验证完关掉本地调试再部署
5. `git add -A && git commit -m "说明"`

### 改接口时注意顺序

前端要审核、云函数立即生效，**云函数的改动必须对线上的旧前端保持兼容**。

比如给报名表加一个必填字段：如果先把云函数改成必填并部署，线上旧前端不传这个字段，
所有报名会立刻失败，而新前端还在审核队列里。正确顺序是：云函数先改成"可选、没传给默认值"
→ 前端加字段并发布 → 用户都更新后再把云函数收紧成必填。

### 加字段要改几处

云函数对写入和返回都用白名单，客户端传什么都只取认识的字段。所以给报名表加字段要改：

1. `pages/signup-form/`：表单控件
2. `hat-signup` 的 `validateSignup()`：否则字段会被**静默丢弃**
3. `hat-signup` 的 `listAll()`：否则组织者那边读不回来
4. `hat-event` 的 `detail()`：如果参与者自己也要看到

代价是加字段麻烦一点，换来的是客户端没法往库里塞任意字段，敏感字段也不会因为忘了过滤而泄露。

## 人不够时：用测试数据

管理员打开任一活动的**管理台**，会看到一张虚线框的「测试数据」卡片（只有管理员可见）：

1. 点「+ 8 人」「+ 16 人」「+ 24 人」，往活动里加一批假报名。名字带「测试」前缀，
   性别约 4 成女生，水平以 3 为中心随机，接近真实俱乐部的分布
2. 照常新建赛事、分队、发布、录比赛、看积分榜

- **测试报名照常占名额**。名额不够时会提示先去「编辑活动」调大人数上限

- 测试账号不会出现在「后台管理」的用户列表里，不会被误设成记分员

### 云函数测试怎么做到不连云

`tests/mock-wx-server-sdk.js` 是云数据库的内存替身，测试时顶掉 `require('wx-server-sdk')`，
5 个云函数能在本机原样跑。替身里所有异步方法都真的让出一次微任务，并发调用会在 `await`
点交错，并发报名的竞态才测得出来。

`cloud.test.js` 里有一个**对照用例**：刻意用"先查后写"的朴素实现跑同样的并发，断言它
**必须超卖**。哪天这条对照用例开始失败，说明测试已经造不出竞态了，"不超卖"的结论也就不可信了。

## 分队算法

`miniprogram/utils/divide.js`，**在小程序端同步执行**（毫秒级，"重新分队"按钮能秒响应，
也省云函数调用配额），云函数只负责校验和持久化。

做法是**约束优先落位 + 按性别分流的蛇形选秀 + 300 次随机重启取最优**。选蛇形选秀，
除了自带随机性、省掉一整套局部搜索代码，还因为**它是组织者本来就有的心智模型**，
结果可解释。有人质疑分队公平性时，这比多 5% 的优化重要得多。

### 硬约束只有两条

只有 **apart（必须拆开）** 和 **同队的人不可拆分** 是硬约束，人数和性别都是软约束、交给
代价函数。把人数上限硬化会在**本来有解的**名单上造成分配失败——带容量的 apart 分配本质是
带容量的图着色，任何一次性贪心都存在失败输入。落位阶段带限定预算的回溯来消掉这类假"无解"。

### 代价函数

```text
cost = 100·人数偏差² + 100·性别偏差² + 100·高分球员偏差² + 1·水平总和偏差²
```

三个容易写错的点：

- **水平项用"总和偏离"，不用"队均值与全局均值之差"。** 队均值在空队时是 `0/0 = NaN`，
  而 `NaN < best` 恒为 false，会让择优**静默失效**且不报错
- **人数项必须单独设。** "男女各自均衡则总人数必然均衡"是错的：各性别的余数可能落在同一队上
  （5 女 10 男分 8 队，重叠那队就是 3 人），而性别项对重叠与否给出完全相同的代价
- **权重是优先级，不是待调参数。** 人数/性别通常能精确达成，水平只能近似，100:1 表示
  "宁可水平差一点，也不用性别失衡去换"

### 性能

| 规模 | 耗时（桌面端） | 人数极差 | 队均水平极差 |
| --- | --- | --- | --- |
| 24 人 / 4 队 | ~60ms | 0 | 0.5 |
| 60 人 / 6 队 | ~180ms | 0 | 0.2 |
| 200 人 / 10 队（各 20 对约束） | ~1.5s | 0 | 0.1 |

耗时主要由**约束数量**决定而不是人数。俱乐部规模下 30 次重启质量就到平台期，300 次是余量；
200 人规模重启还能改善质量，所以没砍。

## 常见问题

**看不到「后台管理」或「测试数据」卡片**
：打开「我的」页看「我的身份」卡片。如果显示「身份查询失败」，按提示处理（通常是 `hat-admin`
没部署）；如果显示「参与者」，说明那个 openid 不在管理员名单里——复制它，按上文「增删管理员」
加进 5 份 `roles.js` 并重新部署。

**云函数报 `FailedOperation.UpdateFunctionCode`，提示"处于 CreateFailed 状态"**
：第一次创建时云端失败了（多半是云端安装依赖时网络抖动），残骸会挡住之后所有上传。
到云开发控制台 → 云函数，删掉那个函数，等一两分钟再重新上传。

**真机调试报 `Error: Timeout`**
：这是开发者工具调试通道连不上，跟小程序代码无关。改用「预览」扫码，预览不走调试通道。
需要在手机上看 console 时，可以试试断开 Tailscale 之类的 VPN、让电脑和手机连同一个 WiFi，
或在「详情 → 本地设置」切换调试基础库（只影响本机调试，不影响用户）。

**改了权限规则但没生效**
：安全规则修改后有 1~3 分钟生效延迟，别急着判断是代码问题。

**云函数改了没效果**
：先确认重新部署了。云函数不部署不会报错，只是跑的还是旧代码。

**提示"云函数 xxx 还没部署"**
：对应目录右键上传部署即可。5 个云函数缺一个，相关页面就打不开。

## 几个需要知道的限制

**免费云环境上线后第 15 天到期。** 未发布前一直免费，**正式版一发布就开始倒计时**，
要提前准备转付费，别被突然停服打到。上传体验版不算发布。

**只有一个云环境。** 个人主体只能开一个免费环境，开发、测试、正式共用一个数据库。
测试数据记得清理：活动名统一加「测试-」前缀，用完在活动编辑页点删除，会级联删掉
该活动的全部报名、赛事、分队和比赛记录。

**不用 `wx.getUserProfile`。** 该接口 2022 年已被回收，只返回灰色头像和"微信用户"。
本项目报名表手填姓名，绕开了这个问题。

**手机号是用户手动填的**，没用 `getPhoneNumber`——那个接口要求已认证的非个人主体，且按条收费。
手机号仅组织者和管理员可见。

**报名防超额没用事务。** 云数据库的事务对象没有 `where` 也没有聚合，"还剩几个名额"这种条件查询
在事务内做不了，且默认只重试 3 次。这里用 `remaining` 字段 + 条件 `where` + `_.inc(-1)`，
看返回的 `stats.updated` 判断是否抢到名额。
