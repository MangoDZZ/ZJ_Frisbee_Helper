# 飞盘 HAT 赛事组织助手

微信小程序。参与者自助报名填报信息，组织者按**水平 + 性别**均衡地随机分队，
支持「必须同队 / 必须拆开」约束和手动微调；赛后录入战绩，积分自动计算。

一个活动里可以开多场赛事，每场按当次赛前检录的人重新分队，积分在活动层汇总。

**要参与开发**请看 [CONTRIBUTING.md](./CONTRIBUTING.md)：分支与 PR 流程、提交前必须跑的测试、
代码风格，以及几个反复踩过的坑。所有测试都是纯 Node，不需要微信环境。

新环境从零搭起来需要两步：

### 1. 建数据库集合

云开发控制台 → 数据库，建这 9 个集合（名字一字不差）：

```text
events  signups  tournaments  divisions  matches  constraints
randomEvents  randomDraws  roles
```

**权限**：每个集合 →「权限设置」→ 自定义安全规则。`events` 填 `{"read": true, "write": false}`，
其余 8 个都填 `{"read": false, "write": false}`（只许云函数读写，原因见
[`数据库安全规则.md`](数据库安全规则.md)）。

**索引**：选中集合 →「索引管理」→ 新建。联合索引按表中顺序添加字段：

| 集合 | 字段（都选升序，除非注明） | 唯一 | 用途 | 优先级 |
| --- | --- | --- | --- | --- |
| `signups` | `eventId` + `openid` | **勾选** | 防止同一人重复报名 | **必须** |
| `signups` | `eventId` + `status` | | 活动报名名单 | 建议 |
| `signups` | `openid` + `status` | | 「我的报名」 | 建议 |
| `signups` | `eventId` + `isTest` | | 清理测试数据 | 可选 |
| `events` | `startTime`（降序） | | 活动列表排序 | 建议 |
| `events` | `ownerOpenid` | | 「我创建的活动」 | 建议 |
| `tournaments` | `eventId` + `createTime` | | 活动下的赛事列表 | 建议 |
| `divisions` | `tournamentId` + `version` | | 读取最新分队 | 建议 |
| `divisions` | `eventId` + `published` | | 积分榜判断是否已发布 | 建议 |
| `matches` | `tournamentId` + `createTime` | | 赛事下的比赛列表 | 建议 |
| `matches` | `eventId` | | 积分榜按活动汇总 | 建议 |
| `constraints` | `eventId` | | 分队约束 | 可选 |
| `roles` | `openid` + `role` | | 判断是不是组织者 / 管理员 | 可选 |

**第一行那个唯一索引不能省**，否则用户连点提交会重复报名、白占名额。其余人少时可以先不建，
但数据积累多了查询会变慢甚至超时。

### 2. 部署 5 个云函数

部署前先跑一次 `node scripts/sync-shared.js`，把 `shared/` 下的共用模块刷进各云函数的
`lib/`；然后右键 `cloudfunctions/` 下的每个目录，选
**「上传并部署：云端安装依赖（不上传 node_modules）」**：

```text
hat-event  hat-signup  hat-team  hat-match  hat-admin
```

`package.json` 里 `wx-server-sdk` 锁在 `~4.0.2`。云端在线安装有可能装到与 Node 版本
不兼容的新版本，所以不要改成 `*` 或 `latest`。

## 集合与索引是什么

**集合**相当于一张表，一类数据放一个集合。每条记录叫一个"文档"，集合之间用 id 互相引用
（比如报名记录里的 `eventId` 指向某个活动）。

| 集合 | 存什么 |
| --- | --- |
| `events` | 活动：时间、地点、人数上限、类型、报名表字段配置、可见性（含 `shareToken` / `visitors`） |
| `signups` | 报名：谁报了哪个活动、性别、自评水平，以及组织者要求采集的年龄/手机号/班级/学号 |
| `tournaments` | 赛事：某活动下的第几场、谁赛前检录了 |
| `divisions` | 分队结果，每次分队存一个版本 |
| `matches` | 比赛：比分、谁上场、MVP、**逐分记录**（`points`：得分队伍 + 得分队员 + 助攻队员） |
| `constraints` | 分队约束：谁和谁必须同队/拆开 |
| `randomEvents` | 随机事件池：说明 + 触发名单 + 效果 |
| `randomDraws` | 已触发的随机事件记录（抽取时存的是快照） |
| `roles` | 组织者名单，以及唯一的管理员 |

**索引**相当于书的目录，让数据库按某个字段查得快，不用逐行翻。人少时没索引也能跑，
但记录越积越多后查询会变慢甚至超时（云数据库超时最常见的原因就是缺索引）。

勾了「唯一」的索引还会**拒绝写入重复的值**，在数据库层面挡住重复报名，
不依赖云函数里的检查有没有漏。

## 使用流程

**组织者**：创建活动 → 分享到群 → 报名截止后在管理台调整水平、设约束 → 关闭报名 →
新建一场赛事、勾选赛前检录的人 → 分队 → 发布 → 每打完一场录一次战绩。
人员变动了可以再开一场赛事重新分队。

### 活动类型

所有活动目前都是**个人积分赛**（`events.type = 'personal'`，界面上显示为类型标签）。
v1.1.3 之前创建的活动文档里没有这个字段，读出来一律按个人积分赛对待。
落库而不是只写文案，是为了以后加「班级赛 / 联赛」时不至于回头补数据——采集字段和积分规则
都会按类型不同，那时再补就晚了。

### 报名表字段由组织者决定

创建/编辑活动页的「报名表字段」决定了报名页长什么样、哪些信息会被收上来：

| 字段 | 能否关闭 | 说明 |
| --- | --- | --- |
| 姓名 / 性别 / 水平 | **不能** | 姓名是整份名单的主键；性别与水平是分队算法的两个均衡维度，关掉就等于放弃均衡 |
| 年龄、手机号、班级、学号 | 能 | 各自可选「采集」和「必填」，必填只在采集时才有意义 |

默认值刻意保守：只采集手机号（选填），其余三项不采集。飞盘 HAT 局不需要年龄和学号，
默认打开只会把报名表撑长。老活动没有这份配置，读出来走同一套默认值，**行为与升级前完全一致**。两个必须知道的实现约束：

- 校验在云函数按活动配置做（`shared/event-config.js`）。不采集的字段**即使提交也一律存空串**，
  否则"这个活动居然收到了学号"是事后无法解释的数据
- 小程序端有一份字段镜像（`miniprogram/utils/signup-fields.js`）：小程序没法 require 仓库根目录，
  云函数也没法引用小程序目录，只能各留一份。`tests/check-pages.js` 会断言两边的字段 key 一致，
  漂移的表现是"组织者勾了年龄，报名页却没有这一栏"，不会报错

### 仅限群聊转发可见

活动编辑页可以勾选「仅限群聊转发可见」：勾上之后活动**不出现在「全部活动」列表里**，
也不能靠猜 id 打开，只能从分享到群里的链接进入。

- 链接里带一个 20 位随机 `shareToken`（不是密码，只是长到猜不中；活动 id 是可能被枚举到的）
- **谁看得到**：组织者/管理员、已报名的人、以及**用带 token 的链接打开过的人**
- 第一次用正确 token 打开时会把这个人记进 `events.visitors`，此后他在活动列表里就能正常看到它
  ——否则"点了链接报名，之后从最近使用进来却找不到"会很怪
- 这个判断挂在**所有按 eventId 读的出口**上（详情、积分榜、数据页、赛事列表、比赛摘要、
  `shared/store.js` 的 `requireEventView`），不只是详情页：只挡详情页而放过积分榜，等于没设

> 它是**可见性**设置，不是安全边界。拿到 id 的人仍然能直接提交报名（报名只校验活动状态和名额）。
> 用途是"内部局别让全群看到"，不是保密。

**赛前检录名单可以整段粘贴。** 赛事页的检录名单上方有个输入框，把群里那句
「1.张三 2.李四 3.王五」直接粘进去点「识别并勾选」即可：编号、备注、逗号/顿号分隔都会自动
去掉，认出的人打勾、认不出的原样列在「未识别名单」里让你手动补。粘一段名单的语义是
**重新勾选**（这些人到场了），不是往上追加——不然默认全选的名单里一个人也取消不掉。

**管理台可以删掉单条报名**（报名名单每行右侧的「删除」），用于重复报名、信息填错、
临时确定不来的人。删掉后名额立刻归还，涉及他的分队约束会自动摘掉（摘完不足 2 人的整条删除）。
已经被某场赛事**赛前检录**的人删不掉 —— 那会留下指向不存在的人的检录记录，得先把他移出
检录名单（或删掉那场赛事）。参与者自己取消报名走活动详情页的「取消报名」，同样在已被检录时
会被拦下，提示联系组织者。

> **活动状态只有「报名中 / 报名关闭」两种，没有「已分队」。** "已分队"是**赛事级**的状态
> （`tournaments.status`），一个活动里的几场赛事可以各自处于不同阶段。所以"能不能改名单"
> 从来不是看活动状态，而是看这个人有没有被哪场赛事检录。

组织者也可以在活动管理台点击「选择 Excel 文件」批量导入名单。表格第一行需要包含
「姓名、性别、能力」三列，能力填写 `L1` 到 `L5`（也接受 `1` 到 `5`）；导入记录会占用活动名额，
并在名单中标记为「导入」。导入名单没有微信账号关联，只用于该活动的赛前检录、分队和比赛记录。

**参与者**：打开活动 → 填姓名、性别、水平自评，以及组织者要求填写的其它项 → 报名 →
分队发布后在赛事里看到自己在哪队 → 随时查积分榜、得分助攻榜和自己的数据。

**比赛记录有两处入口**：活动详情页的「比赛记录」卡片（直接显示最近两场的比分，点进去就是
比赛记录界面），以及「赛事 → 某场赛事 → 比赛记录」。前者是为"打完想马上看/马上录"准备的，
不用再点三层。

**组织者**：打开赛事 → 比赛记录 → 三阶段记一场比赛（检录 → 逐分记录 → 结束）。

**赛前先在「比赛记录」页配规则**（右上角「赛前配置」）：初始目标分、中场时刻、软时限、
硬时限（选填）、中场休息时长。规则存在**赛事级**，对这场赛事之后录的每场比赛生效。

## 记一场比赛：三个阶段

单场比赛页跟着比赛进程走，顶部有阶段指示：

| 阶段 | 做什么 |
| --- | --- |
| ① 赛前检录 | 选对阵的两支队，勾出**这场**实际上场的人（默认全队，取消没来的）。赛事层的报名名单检录在赛事页，是分队范围。这里有「本场备注」 |
| ② 比赛中 | **逐分记录**：每记一分选「得分队伍 + 得分队员 + 助攻队员」，同时记下这一分发生在第几分钟。助攻可留空（个人单打）。记错随时撤销某一分 |
| ③ 比赛结束 | 看最终比分与用时，登记**弃赛**、选**本场 MVP**，然后「结束并保存」 |

三个要点：

- **比分不是手填的**，它由逐分记录条数算出来，所以比分和明细永远一致
- **每记一分自动暂存**：加/删/撤销任何一分都会立刻把当前明细写进库（状态记成**进行中**），
  比赛中闪退、切后台、被人打断，回来打开这场比赛的「继续记录」能接着记，
  比赛列表上会标「进行中」。写完没有任何弹窗，只在比分条下面留一行「已自动暂存 21:04」
- **进行中的比赛允许平局**（比如记到 1:1 就得先离开），结束一场比赛才不允许同分——
  先把比赛标成结束、再回头补分的做法会让积分榜短时间多算一场
- **进行中的比赛也计入积分**（否则记分员忘了点「比赛结束」就会静默少分），
  积分榜会提示还有几场没结束

## 比赛规则与时间轴

「比赛记录」页的「赛前配置」决定这场赛事的比赛怎么结束、什么时候中场。规则存在**赛事级**
（`tournaments.matchRules`），默认值：

| 配置 | 默认 | 作用 |
| --- | --- | --- |
| 初始目标分 | 13 | 任一队到达即比赛结束 |
| 中场时刻 | 30 分 | 中场时刻的"时间分支" |
| 软时限 | 60 分 | 到点之后的**下一次得分完成时**，场上领先方 +1 成为新目标分 |
| 硬时限 | 不设 | 到点必须结束，与比分无关 |
| 中场休息 | 3 分 | 只是提示用的倒计时 |

**中场时刻 = 较早者**：「中场时刻」（默认 30 分）与「任一队达到 ceil(目标分/2)」（13 → 7 分）
哪个先到算哪个。分数分支让领先的一局打得快就早中场，时间分支兜住一直不得分的情况。

四个容易搞错的点：

- **软时限不改在"到点那一刻"**。规则是"到点后的下一次得分完成时"，所以到点后还没得分时目标分
  不变，页面上会提示"下一次得分后目标分将调整为领先方 +1"
- **目标分只会被抬高，不会被压低**。软时限后领先方 6 分时算出新目标 7，但初始目标已是 13，
  就仍按 13
- **硬时限到点但平局时不能结束**（结束的比赛不允许平局）。页面提示"请继续记到分出胜负"，
  这等于突然死亡；分出来之后才能点结束
- **中场休息不停表**。倒计时只是提示，比赛用时照走——这是计划书明确要求的，
  和"停表"的规则不一样

**开表是显式动作。** 进入「比赛中」后要先点「开始计时」，服务端才记下 `startedAt`。
不让"进第二阶段"自动开表，是因为那会凭空在比赛列表里创建一条 0:0 的进行中记录，
点错标签页也会留下垃圾数据。不开表也能记分，只是没有时间轴和中场提示。

**得分时刻存的是"相对开表的秒数"**（`points[].t`），不是设备时间戳：设备时钟差几分钟是常事，
相对秒数不受影响。服务端按 `startedAt + t*1000` 算出绝对时刻给页面显示。
事后补记的比赛没有 `t`（时间轴显示"—"），其余一切照旧。

**规则快照。** 创建比赛时会把当时的规则存进 `matches.matchRules`，所以组织者之后改了赛事规则，
已经打完的比赛仍按当时的规则解释，历史不会被倒改。

**本场备注**是每场单独填的（`matches.notes`，最多 200 字），显示在「比赛记录」界面的那张卡片上。

## 得分 / 助攻数据

活动层级有两处数据页：

**得分助攻榜**（活动详情 → 查看数据）：三张榜并排看，每张**至多前 15 名**、按对应数据降序，
同分并列同名次。

```text
得分榜          按得分降序
助攻榜          按助攻降序
得分 + 助攻榜    按两者之和降序
```

**我的数据**（活动详情「我的报名」→ 我的数据，或「我的」页对应活动）：报名者看自己的
得分、助攻、得分+助攻合计，以及逐场明细。

积分榜里「同分时比得分+助攻」用的就是同一个合计值，所以在这两处看到的数字一定一致。

两者都**只统计有逐分明细的比赛**——升级前录入的比赛只有比分，分不出谁得了哪一分。
所以榜单上的场次数可能小于积分榜的场次数，页面会明确写出差了哪几场，而不是让人以为统计漏了。

## 随机事件（活动级）

给比赛添点意外。入口：**管理台 → 随机事件**（组织者/管理员可见），或活动详情底部。

玩法分两步：

**1. 先准备事件池。** 每个事件三样东西：

| 字段 | 说明 | 约束 |
| --- | --- | --- |
| 说明 | 例「踩到边界线」 | 必填，≤ 60 字 |
| 效果 | 加分或减分 | ±1 ~ ±10 的整数，不能为 0 |
| 触发名单 | 这个事件发生时会作用到谁 | 至少 1 人，只能选本活动的报名者 |

**2. 需要时点「抽取」。** 服务端从池子里**随机抽一个**，效果立刻作用到它自己的触发名单上
并计入积分榜；抽中的事件会弹出来给大家看。抽中的事件**留在池子里**，可以继续抽。

几个设计上的决定：

- **随机在服务端做。** 客户端拿不到池子（成员名单对参与者保密，惊喜才有意思），
  而抽中的结果要落库——落库的东西就不该由客户端说了算
- **触发记录存快照**（说明 + 效果 + 名单），不引用事件池的 id。池子是覆盖式保存的，
  id 每次都会变，引用它必然悬空
- **每次抽取都能撤销**，撤销后那笔调整立刻从积分榜上消失（积分是实时推导的）
- **删掉报名时，会把他从事件池的触发名单里摘掉**（摘完一个人不剩就删掉那条事件）。
  不摘的话那条事件以后被抽中会**静默少算几个人**——组织者看着是"这 5 人各扣 1 分"，
  实际只扣了还在的人，这种错最难发现。已触发的记录不动，那是当时确实发生过的历史

参与者也能在积分榜上看到**最近 20 条**触发记录（含人名和分值，不含手机号/水平），
这样"我的分怎么变了"有据可查。查看门槛与积分榜一致：分队未发布时参与者看不到。

## 用户角色

| 角色 | 怎么认定 | 能做什么 |
| --- | --- | --- |
| 参与者 | 默认 | 报名、查看积分榜与战绩。**不能发起活动** |
| 组织者 | `roles` 集合，管理员指定 | 发起活动，并管理**所有**活动的报名、赛前检录、分队、战绩与积分 |
| 管理员 | `roles` 集合里的 `role: admin` 记录，同时只有一个 | 组织者的全部权限，外加增删组织者、移交管理员身份 |

管理员可以操作任何人创建的活动。**活动的创建者也归在组织者这一侧**：活动是他建的，就
永远归他管（组织者身份被取消后也不会把自己的活动锁死），只是不能再发起新活动。

### 怎么进别人的管理台

组织者和管理员能管理**任何**活动，入口有两处：

- 「活动」页 → 「全部活动」列表：能管的活动，卡片下方有「进入管理台」按钮
- 打开任一活动详情 → 底部「管理台」按钮（`canManage` 为真时显示）

进到别人的活动时，管理台顶部会写明「这场活动不是你创建的」。参赛的普通用户看不到这两个
入口，直接改 URL 也会被云函数拒绝。

### 查看自己的身份

打开「我的」页：

- 管理员：顶部显示「管理员」卡片，可进「后台管理」
- 组织者：顶部显示「组织者」卡片，可以进后台看名单（但改不了）
- 参与者：什么都没有

### 指定组织者（在小程序里操作）

用管理员账号进「我的」→「后台管理」，列表里是所有报过名的人，点某人 → 选「设为组织者」。

- **报过名的人排前面**，按最近一次报名时间倒序；想让某人当组织者，先让他随便报一场活动
- **只有角色、没有报名记录的人也会列在最后**，带「无报名」标签。组织者身份存在 `roles` 集合里，
  报名记录删了权限还在——不给这类人留一行，就会出现一个看不见也撤不掉的权限
- 对方要重新进一次「我的」页才会看到身份变化
- 组织者只能看名单，增删组织者仍然只有管理员能做

### 当前版本号

「后台管理」页最下面的「关于」卡片显示当前小程序版本（`miniprogram/config.js` 的 `VERSION`）。
反馈问题时先看这个——线上跑的是哪一版，只有这里能确认。
`tests/check-pages.js` 会断言它与 `plan.md` 最新一节一致，发版忘了改版本号会直接报错。

### 移交管理员身份（在小程序里操作）

「后台管理」→ 点某人 → 「移交管理员身份给他」。

- **这是不可撤销的自我降级**：移交完成后你自己立刻失去后台权限，而且无法自己拿回来
- 同一时间只有一个管理员，移交是真正的"转移"，不是再加一个人
- 只能移交给真实报过名的人（测试数据和导入名单没有微信账号）

### 初始管理员（要改代码）

新环境里数据库还没有管理员记录，这时云函数里写死的 `ADMIN_OPENIDS` 就是初始管理员，
用来把你带进后台。**一旦完成一次移交，这份名单就自动失效**——否则权限根本交不出去。

要换初始管理员（比如换了云环境、或管理员记录被误删）：

1. 拿到对方的 openid：让他报名任意活动，再到「后台管理」列表或云开发控制台
   `signups` 集合里找他那条记录的 `openid` 字段
2. 把 openid 加进 `shared/roles.js` 的 `ADMIN_OPENIDS`
3. 跑 `node scripts/sync-shared.js` 同步到 5 个云函数（见下文"共用模块"）
4. 双击 `run-tests.cmd`，然后 5 个云函数全部重新部署

### 共用模块：改 `shared/`，跑同步脚本

云函数各自独立部署，部署包里只有自己那个目录，没法 `require` 外面的代码，所以每个云函数
的 `lib/` 下都要放一份副本。但**源头只允许有一个**：

```text
shared/                 ← 唯一可改的地方
├── common.js           ok/err/asInt/分页取全等小工具
├── event-config.js     活动类型、报名表字段规格与校验、可见性
├── match-rules.js      比赛规则与时间轴（纯 JS，云函数和小程序共用）
├── roles.js            角色与权限判定（含初始管理员名单、canViewEvent）
└── store.js            loadEvent / loadTournament / loadSignups / requireEventView

node scripts/sync-shared.js   ← 改完 shared/ 必须跑一次，把副本刷到 cloudfunctions/*/lib/
                                 以及 miniprogram/utils/（只对纯 JS 的模块）
```

`match-rules.js` 是个特例：它**不碰 wx、也不碰 Node**，所以同一份源码两个运行时都能跑。
同步脚本除了拷进 `hat-match/lib/`，还会拷一份到 `miniprogram/utils/`。这样"目标分 13、中场 30 分"
这类常量只有一处，不会出现"组织者改成 15、记分页还按 13 提示可以结束"。
`tests/check-pages.js` 会断言副本与源头逐字节一致，并检查它没有偷偷用 `wx.` 或外部包。

`cloudfunctions/*/lib/` 下的同名单文件是**生成物，不要直接改**。以前 5 份 `roles.js` 靠手改，
漏改一份的后果很隐蔽：这个人在某些功能里是管理员、在另一些里不是，表现为"有的按钮能点，
有的点了报没权限"。现在 `run-tests.cmd` 会断言副本与 `shared/` 完全一致，忘了同步就会红。

## 层级结构

```text
活动 event          报名在这一层
 └── 赛事 tournament  各自记录赛前检录名单、各自随机分队
      └── 分队 division
           └── 比赛 match  记录比分、谁上场、MVP
```

两个层次的"参与"不要混淆：

- **赛前检录**（赛事级）：这场赛事谁来了，决定分队范围
- **上场**（比赛级）：某一场比赛谁实际打了，决定得分

分队约束挂在**活动**层（"这两个人别同队"对每场赛事都适用，不用重设）。某场赛事有人没检录时，
分队前会自动把缺席的人从约束里摘掉，剩不足 2 人的整条忽略，页面上会提示忽略了几条。

## 积分规则

| 情况 | 积分 |
| --- | --- |
| 所在队伍**获胜** | +3 |
| 所在队伍**落败** | +1 |
| 当选**本场 MVP** | 额外 +1 |
| **弃赛** | -3 |
| **未上场** | 不计分 |
| **随机事件** | 按事件设置的 ±1 ~ ±10 |

**总分 = 比赛积分 + 随机事件调整。** 两个来源在积分榜上分开留档（每行带 `matchPoints`
和 `eventDelta`），页面上会写「含随机事件 +N」——否则看到"没上场却有分"会以为算错了。

- MVP 由**胜方从败方的上场队员中选出 2 名**（单向，胜方队员拿不到 MVP 分），可以先不选、之后补录
- 弃赛人员本场不计胜负分，额外扣 3 分；活动内累计弃赛 2 次及以上，最终积分归零
- **结束的比赛不允许平局**，比分相同时「结束并保存」会报错；比赛中（进行中）可以先存着
- 平局时**不区分胜败方**，所以 MVP 不做"必须来自败方"的校验（只校验选的人本场上过场）
- 积分榜是**活动级汇总**：把该活动下所有赛事的得分按人合并，不跨活动累计
- **积分相同时，按「得分 + 助攻」的总数排名**，名次也就此分出先后（不再并列）。
  两者都相同才继续比胜场、MVP 数。榜单每行会显示「得分 x · 助攻 y（共 z）」，
  所以名次先后能自己核对；`z` 与「查看数据」页的得分助攻榜是同一套数
- **判弃赛的人必须先不在上场名单里**（两件事互斥，不是"既上场又弃赛"）
- **累计弃赛归零会把随机事件调整一起归零**——规则说的是"积分归零"，那就该看到 0。
  事件调整的数额仍留在 `eventDelta` 里，页面上能解释这笔分是怎么没的

四个实现上的决定：

**积分不入库，每次由比赛记录和随机事件记录实时推导**（`cloudfunctions/hat-match/lib/score.js`）。
存一份积分字段就一定会漂移——改一次比分、删一场比赛、换一次 MVP、撤销一次抽取，
存量数字就对不上了。分值在文件顶部的常量（`WIN` / `LOSS` / `MVP_BONUS` / `FORFEIT`），要调改一行。

**"累计弃赛归零"最后一步才执行。** 先把比赛分和事件调整都算完，再对触发规则的人把总分置 0，
所以是真正的归零；同时保留 `matchPoints` / `eventDelta` 供页面解释。

**"得分 + 助攻"和得分助攻榜共用同一个累计函数**（`accumulatePoints`）。并联判定拿它做第一
并列条件，页面也展示它——两处各写一遍的话，同一个人在积分榜和数据页看到的进球数会不一样，
名次就无从解释了。只有**有逐分明细**的比赛才计入，老比赛没有明细，所有人的这一项都是 0，
排序退回原来的"胜场 → MVP → 姓名"。

**比分从逐分记录算出来，客户端传什么都不采信。** 有 `points` 明细时，`scoreA` / `scoreB`
由明细重新数一遍再入库；没有明细（升级前的老比赛、旧版前端）才沿用客户端手填的比分。
两条路并存，所以新旧前端在部署窗口期内都能提交。

**进行中的比赛照样计分。** 反过来（只算已结束的）会有一个很难查的后果：记分员忘了点
「比赛结束」，那场比赛的积分就静默消失了。现在的取舍是照常计入，并在积分榜上提示
"还有 N 场进行中，数字未定稿"。

**录入比赛后，该赛事禁止重新分队、禁止改赛前检录名单。** 比赛记录引用的是队伍序号和队员 id，
重新分队会让引用全部失效。要重分得先删掉这场赛事的比赛记录。

## 球员水平不公开

参与者**只能看到自己的自评**，看不到组织者调整后的值，也看不到任何别人的水平。
队均水平和高分人数同样只对组织者和管理员可见。

实现上在**云函数出口剥离**，不是靠前端不渲染——前端不渲染，数据照样发到了客户端，
在调试工具里一看就有。测试里用 `JSON.stringify` 全文断言参与者拿到的返回不含任何 `level` 字段。

**队内名单按姓名排，不按水平排。** 分队结果是发布给所有人看的，如果按水平从高到低列出，
等于把组织者对每个人的评级直接念出来——看一眼名单顺序就知道谁被评了 5 分。
姓名序（中文按拼音）对谁都不透露信息。组织者自己仍然看得到每人的水平标注和队均水平。

## 修改代码后怎么生效

**前端和云函数的生效方式完全不同**，这是最容易踩的坑：

| 改动 | 生效方式 | 线上用户何时看到 |
| --- | --- | --- |
| `miniprogram/` 下任何文件 | 保存后开发者工具自动重编译 | 上传 → 提审 → 发布之后 |
| `shared/` 下任何文件 | 先跑 `node scripts/sync-shared.js`，再部署云函数 | **部署后几秒，不经审核** |
| `cloudfunctions/` 下任何文件 | **必须右键重新上传部署** | **部署后几秒，不经审核** |
| 数据库数据、权限、索引 | 在控制台改 | 立即（权限规则有 1~3 分钟延迟） |

三个后果：

- **云函数改了不部署，不会报任何错**，只是改动静默不生效
- **云函数没有审核兜底**。开发版、体验版、正式版共用同一个云环境，部署一个有 bug 的
  云函数就是线上事故
- 改了 `shared/` 忘了跑同步脚本，`run-tests.cmd` 会报"副本不一致"；忘了重新部署，
  改动一样不生效

### 建议的修改流程

1. 改动前 `git status` 确认工作区干净
2. 改代码（改的是 `shared/` 下的文件就顺手跑 `node scripts/sync-shared.js`）
3. 双击 `run-tests.cmd`，确认全部通过
4. 改了云函数：先右键「开启云函数本地调试」验证，**线上用户此时仍跑云端旧版本**；
   验证完关掉本地调试再部署
5. `git add -A && git commit -m "说明"`

### 改接口时注意顺序

前端要审核、云函数立即生效，**云函数的改动必须对线上的旧前端保持兼容**，反过来也一样：
新前端会有一段时间跑在旧云函数上。

比如给报名表加一个必填字段：如果先把云函数改成必填并部署，线上旧前端不传这个字段，
所有报名会立刻失败，而新前端还在审核队列里。正确顺序是：云函数先改成"可选、没传给默认值"
→ 前端加字段并发布 → 用户都更新后再把云函数收紧成必填。

同理，前端读云函数返回的字段时**要自带兜底**——积分榜的规则文案就是这么处理的，
旧云函数不回 `forfeit` 字段时用默认值顶上，而不是显示成「弃赛 undefined」。

### 加字段要改几处

云函数对写入和返回都用白名单，客户端传什么都只取认识的字段。所以给报名表加字段要改：

1. `pages/signup-form/`：表单控件
2. `hat-signup` 的 `validateSignup()`：否则字段会被**静默丢弃**
3. `hat-signup` 的 `listAll()`：否则组织者那边读不回来
4. `hat-event` 的 `detail()`：如果参与者自己也要看到

代价是加字段麻烦一点，换来的是客户端没法往库里塞任意字段，敏感字段也不会因为忘了过滤而泄露。

**如果这个字段应该由组织者决定采不采集**（像年龄/班级/学号那样），就别硬编码，加进
`shared/event-config.js` 的 `CONFIGURABLE_FIELDS` 和 `miniprogram/utils/signup-fields.js` 的
同名列表即可：配置界面、报名页渲染、云函数校验、默认值全都由这两份数据驱动。
`tests/check-pages.js` 会断言两边字段 key 一致。

## 人不够时：用测试数据

管理员打开任一活动的**管理台**，会看到一张虚线框的「测试数据」卡片（只有管理员可见）：

1. 点「+ 8 人」「+ 16 人」「+ 24 人」，往活动里加一批假报名。名字带「测试」前缀，
   性别约 4 成女生，水平以 3 为中心随机，接近真实俱乐部的分布
2. 照常新建赛事、分队、发布、录比赛、看积分榜
3. 测完点「清理 N 个测试报名」

几个规则：

- **测试报名照常占名额**。名额不够时会提示先去「编辑活动」调大人数上限
- **测试选手已经进了某场赛事时，不能直接清理**，要先删掉那场赛事（删赛事会连带清掉它的分队
  和比赛）。否则分队和比赛记录里会留下指向不存在的人的数据
- 清理时，约束里涉及测试选手的部分会被摘掉；摘完不足 2 人的约束整条删除
- 测试账号不会出现在「后台管理」的用户列表里，不会被误设成组织者或管理员

## 测试

没装就自动用 VS Code 自带的 Node 运行时。命令行等价于 `node tests/run-all.js`。

推送到 GitHub 后，`.github/workflows/tests.yml` 会在每次 push 到 `main` 和每个 PR 上
自动跑同一套测试（ubuntu + Node 20），PR 上红了就别合。

| 套件 | 覆盖 |
| --- | --- |

### 云函数测试怎么做到不连云

`tests/mock-wx-server-sdk.js` 是云数据库的内存替身，测试时顶掉 `require('wx-server-sdk')`，
5 个云函数能在本机原样跑。替身里所有异步方法都真的让出一次微任务，并发调用会在 `await`
点交错，并发报名的竞态才测得出来。

`cloud.test.js` 里有一个**对照用例**：刻意用"先查后写"的朴素实现跑同样的并发，断言它
**必须超卖**。哪天这条对照用例开始失败，说明测试已经造不出竞态了，"不超卖"的结论也就不可信了。

## 分队算法

`miniprogram/utils/divide.js`，**在小程序端同步执行**（毫秒级，"重新分队"按钮能秒响应，
也省云函数调用配额），云函数只负责校验和持久化。

做法是**约束优先落位 + 按性别分流的蛇形选秀 + 1000 次随机重启取最优**。选蛇形选秀，
除了自带随机性、省掉一整套局部搜索代码，还因为**它是组织者本来就有的心智模型**，
结果可解释。有人质疑分队公平性时，这比多 5% 的优化重要得多。

### 硬约束只有两条

只有 **apart（必须拆开）** 和 **同队的人不可拆分** 是硬约束，人数和性别都是软约束、交给
代价函数。把人数上限硬化会在**本来有解的**名单上造成分配失败——带容量的 apart 分配本质是
带容量的图着色，任何一次性贪心都存在失败输入。落位阶段带限定预算的回溯来消掉这类假"无解"。

### 代价函数

```text
cost = 50·人数偏差² + 100·性别偏差² + 100·高分球员偏差² + 50·(水平总和偏差² / μ²)
```

`μ` 是全员平均水平。**高分球员**指水平达到 `STAR_LEVEL`（当前为 5）的人。四个权重集中在
`divide.js` 顶部的 `WEIGHTS` 里，改权重只需改那一行，`tests/divide.test.js` 会跟着
`STAR_LEVEL` 走、并校验"分项明细"和"总分"始终出自同一套公式。

三个容易写错的点：

- **水平项用"总和偏离"，不用"队均值与全局均值之差"。** 队均值在空队时是 `0/0 = NaN`，
  而 `NaN < best` 恒为 false，会让择优**静默失效**且不报错
- **人数项必须单独设。** "男女各自均衡则总人数必然均衡"是错的：各性别的余数可能落在同一队上
  （5 女 10 男分 8 队，重叠那队就是 3 人），而性别项对重叠与否给出完全相同的代价
- **权重是优先级，不是待调参数。** 人数/性别通常能精确达成，水平只能近似，50:100 表示
  "宁可水平差一点，也不用性别失衡去换"。水平项按 `μ²` 归一化后，"偏离 1 档"在 `μ=3` 时
  折合 5.6 分，所以 `WEIGHTS.level = 50` 已经让水平均衡和人数偏差同等重要——再往上调就会
  拿性别换水平

### 性能

| 规模（`tests/divide.test.js` 里的 perf 用例，桌面端） | 耗时 | 人数极差 | 队均水平极差 |
| --- | --- | --- | --- |
| 24 人 / 4 队 | ~10ms | 0 | 0.17 |
| 60 人 / 6 队（6 对同队 + 3 对拆开） | ~50ms | 0 | 0.20 |
| 200 人 / 10 队（各 20 对约束） | ~260ms | 0 | 0.00 |

耗时主要由**约束数量**决定而不是人数。手机上按实测的 3~5 倍估算，仍然远低于"重新分队"
按钮的可接受等待。真要再快，`restarts` 是最直接的旋钮（默认 1000 次），调低只是少了些
重启取样，不会让硬约束失效。

## 常见问题

**看不到「后台管理」或「测试数据」卡片**
：打开「我的」页看「我的身份」卡片。如果显示「身份查询失败」，按提示处理（通常是 `hat-admin`
没部署）；如果显示「参与者」，说明那个 openid 既不是组织者也不是管理员——复制它，
按上文「指定组织者」加进去即可。

**云函数报 `FailedOperation.UpdateFunctionCode`，提示"处于 CreateFailed 状态"**
：第一次创建时云端失败了（多半是云端安装依赖时网络抖动），残骸会挡住之后所有上传。
到云开发控制台 → 云函数，删掉那个函数，等一两分钟再重新上传。

**真机调试报 `Error: Timeout`**
：这是开发者工具调试通道连不上，跟小程序代码无关。改用「预览」扫码，预览不走调试通道。
需要在手机上看 console 时，可以试试断开 Tailscale 之类的 VPN、让电脑和手机连同一个 WiFi，
或在「详情 → 本地设置」切换调试基础库（只影响本机调试，不影响用户）。

**改了权限规则但没生效**
：安全规则修改后有 1~3 分钟生效延迟，别急着判断是代码问题。

**云函数改了没效果**
：先确认重新部署了。云函数不部署不会报错，只是跑的还是旧代码。

**提示"云函数 xxx 还没部署"**
：对应目录右键上传部署即可。5 个云函数缺一个，相关页面就打不开。

## 几个需要知道的限制

**免费云环境上线后第 15 天到期。** 未发布前一直免费，**正式版一发布就开始倒计时**，
要提前准备转付费，别被突然停服打到。上传体验版不算发布。

**只有一个云环境。** 个人主体只能开一个免费环境，开发、测试、正式共用一个数据库。
测试数据记得清理：活动名统一加「测试-」前缀，用完在活动编辑页点删除，会级联删掉
该活动的全部报名、赛事、分队和比赛记录。

**不用 `wx.getUserProfile`。** 该接口 2022 年已被回收，只返回灰色头像和"微信用户"。
本项目报名表手填姓名，绕开了这个问题。

**手机号是用户手动填的**，没用 `getPhoneNumber`——那个接口要求已认证的非个人主体，且按条收费。
手机号仅组织者和管理员可见。

**报名防超额没用事务。** 云数据库的事务对象没有 `where` 也没有聚合，"还剩几个名额"这种条件查询
在事务内做不了，且默认只重试 3 次。这里用 `remaining` 字段 + 条件 `where` + `_.inc(-1)`，
看返回的 `stats.updated` 判断是否抢到名额。
