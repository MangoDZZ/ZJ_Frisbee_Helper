# 飞盘 HAT 赛事组织助手

微信小程序。参与者自助报名填报信息，组织者一键按**水平 + 性别**均衡地随机分队，
支持「必须同队 / 必须拆开」约束和手动微调。

## 跑起来需要做的四件事

### 1. 填 AppID

`project.config.json` 里把 `"appid": "TODO_你的小程序AppID"` 换成你的 AppID。

> 云开发**不支持测试号**，必须用正式注册的小程序 AppID。

### 2. 开通云开发并填环境 ID

微信开发者工具顶部点「云开发」→ 开通环境（有免费额度）。

然后把环境 ID 填到 `miniprogram/config.js`：

```js
const ENV_ID = '你的环境ID'
```

> 用**开发者工具内**云开发控制台显示的那个环境 ID，不是网页版控制台的。
> 这个值必须显式写死——`wx.cloud.init` 不传 `env` 会连到"默认环境"（第一个创建的那个），
> 多环境时是反复踩的坑。

### 3. 建数据库集合、设权限、建索引

照 [`数据库安全规则.md`](数据库安全规则.md) 做。**`signups` 上的联合唯一索引不能省**，
否则用户连点提交会重复报名。

### 4. 部署三个云函数

在开发者工具里分别右键 `cloudfunctions/hat-event`、`hat-signup`、`hat-team`、`hat-match`、`hat-admin`，
选 **「上传并部署：云端安装依赖（不上传 node_modules）」**。

> 选云端安装依赖，`node_modules` 就不占上传体积，冷启动更快。
> `package.json` 里 `wx-server-sdk` 已经用 `~4.0.2` 锁到小版本——云端在线安装
> 有可能装到与 Node 版本不兼容的新版本，所以不要改成 `*` 或 `latest`。

做完这四步，编译运行即可。

## 使用流程

**组织者**：创建活动 → 分享到群 → （报名截止后）管理台调整水平、设约束 →
关闭报名 → 新建一场赛事并勾选到场的人 → 分队 → 发布 →
每打完一场录一次战绩。人到齐了可以再开一场赛事重新分队，积分在活动层汇总。

**参与者**：打开活动 → 填姓名/性别/水平自评/手机号（选填）→ 报名 →
发布后在活动详情页看到自己在哪队 → 比赛进行中随时查积分榜。

## 分队算法

`miniprogram/utils/divide.js`，**在小程序端同步执行**（毫秒级，所以"重新分队"
按钮能秒响应，也省云函数调用配额），云函数只负责校验和持久化。

做法是**约束优先落位 + 按性别分流的蛇形选秀 + 300 次随机重启取最优**。

选蛇形选秀而不是"贪心 + 局部搜索"，除了它自带随机性、省掉一整套局部搜索代码之外，
还有一个实际理由：**蛇形选秀是组织者本来就有的心智模型**（"我们按蛇形分的"），
结果可解释。有人质疑分队公平性时，这比多 5% 的代价优化重要得多。

### 硬约束只有两条

只有 **apart（必须拆开）** 和 **pod 不可拆分** 是硬约束，人数和性别一律是软约束、
交给代价函数。把人数上限硬化会在**本来有解的**名单上造成分配失败——带容量的
apart 分配本质是带容量的图着色，NP-hard，任何一次性贪心都存在失败输入。

阶段 1 落位带**限定预算的回溯**，正常名单上开销几乎为零，但能消掉那类假"无解"。

### 性能

实测（桌面端，含 300 次重启）：

| 规模 | 耗时 | 人数极差 | 队均水平极差 |
| --- | --- | --- | --- |
| 24 人 / 4 队 | ~60ms | 0 | 0.5 |
| 60 人 / 6 队 | ~180ms | 0 | 0.2 |
| 200 人 / 10 队（各 20 对约束） | ~1.5s | 0 | 0.1 |

**耗时主要由约束数量决定，不是人数**：200 人无约束只要 50ms，加上 40 条约束就变成 1.5s
——开销在带 apart 约束的 pod 落位（带回溯的搜索）上。

另外实测发现：**俱乐部规模下质量在 30 次重启就到平台期**了（30 次和 300 次的代价完全相同），
300 次只是白送的余量。但 200 人规模重启确实还能改善质量（30 次 → 300 次代价从 180 降到 40），
所以没有为了提速去砍重启次数。

200 人已超出"小型俱乐部"这个场景，手机上可能要几秒。真要支持这种规模，
下一步该做的是把 `divide.js` 里按字符串键访问的计数（`team.count[cls]`）改成
三个独立数字字段——那是当前的热点。

### 代价函数

```text
cost = 100·人数偏差² + 100·性别偏差² + 100·高分球员偏差² + 1·水平总和偏差²
```

三个容易写错的点，都在代码注释里标了：

- **水平项用"总和偏离"，不用"队均值与全局均值之差"。** 队均值在空队时是
  `0/0 = NaN`，而 `NaN < best` 恒为 false，会让择优**静默失效**且不报错。
- **人数项必须单独设。** "男女各自均衡则总人数必然均衡"是错的：各性别的余数
  可能落在同一队上（5 女 10 男分 8 队时，女有 5 个余数队、男有 2 个，重叠的那队
  就是 3 人），而性别项对重叠与不重叠给出**完全相同**的代价，分不出好坏。
- **权重是优先级语义，不是待调参数。** 人数/性别在真实名单里通常可精确达成，
  水平只能近似，所以 100:1 表示"宁可水平差一点，也不用性别失衡去换水平收益"。

## 用户角色

| 角色 | 怎么认定 | 能做什么 |
| --- | --- | --- |
| 一般参与者 | 默认 | 报名、查看积分榜与战绩 |
| 记分员 | `roles` 集合，管理员指定 | 录入/修改比赛战绩 |
| 组织者 | 活动创建者 | 创建活动与赛事、管理报名、调整水平、分队、发布 |
| 管理员 | 云函数里写死的 openid 白名单 | 管理记分员，并拥有全部组织者权限 |

管理员名单在 `cloudfunctions/*/lib/roles.js` 的 `ADMIN_OPENIDS` 里。这份文件在
**每个云函数里各有一份副本**（云函数独立部署，没法跨目录共享代码），改名单要改全部
5 份并重新部署——`tests/check-pages.js` 会检查副本是否一致，漂移了会报错。

**为什么不放在前端 config.js**：那是客户端代码，改一行就能冒充管理员。权限一律在
云函数里判，前端的角色信息只用来决定按钮显不显示。

## 层级结构

```text
活动 event（报名在这一层）
 └── 赛事 tournament（各自记录到场名单、各自随机分队）
      └── 分队 division
           └── 比赛 match（记录谁上场、比分、MVP）
```

一个活动可以开多场赛事，**每场赛事各自统计当次到场的选手并重新随机分队**。
积分榜是**活动级汇总**，把该活动下所有赛事的得分按人合并。

两个层次的"参与"不要混淆：

- **到场**（赛事级）：这场赛事谁来了，决定分队范围
- **上场**（比赛级）：某一场比赛谁打了，决定得分

## 球员水平不公开

参与者**只能看到自己的自评**，看不到组织者调整后的值，也看不到任何别人的水平。
队均水平和高分人数同样只对组织者/管理员可见。

实现上在**云函数出口剥离**，不是靠前端不渲染——前端不渲染，数据照样发到了客户端，
在调试工具里一看就有。`tests/cloud.test.js` 里用 `JSON.stringify` 全文断言参与者
拿到的返回里不含任何 `level` 字段。

记分员也看不到水平，他只需要名字就能录战绩。

## 积分规则

打完一场比赛由组织者录入战绩，个人积分自动算出来：

| 情况 | 积分 |
| --- | --- |
| 所在队伍**获胜** | +3 |
| 所在队伍**落败** | +1 |
| 当选**本场 MVP** | 额外 +1 |
| **未上场** | 不计分 |

- MVP 由**胜方从败方的上场队员中选出 2 名**（单向，胜方队员拿不到 MVP 分）
- **不允许平局**，比分相同时录入直接报错
- 积分**按单场活动独立统计**，不跨活动累计

两个实现上的决定：

**积分不入库，每次由比赛记录实时推导**（`cloudfunctions/hat-match/lib/score.js`）。存一份积分字段就一定会漂移——改一次比分、删一场比赛、换一次 MVP，存量数字就对不上了。规则分值是文件顶部的三个常量，要调改一行。

**录入比赛后禁止重新分队**。比赛记录引用的是队伍序号和队员 id，重新分队会让这些引用全部失效，产生"某人的积分属于一支已经不存在的队"这种说不清的状态。要重分得先删掉全部比赛记录。

## 跑测试

测试**完全不需要微信环境**，纯 Node 即可：

```bash
node tests/run-all.js
```

三个套件：

| 套件 | 覆盖 |
| --- | --- |
| `divide.test.js` | 分队算法：边界、约束满足、可复现性、500 组模糊测试 |
| `score.test.js` | 积分推导：计分规则、跨赛事汇总、未上场不计分、MVP、排序 |
| `cloud.test.js` | 云函数逻辑：角色权限矩阵、水平保密、并发不超卖、赛事与比赛校验 |
| `check-pages.js` | 页面静态一致性：WXML 绑定、字段引用、云函数 action、roles.js 副本一致 |

### 本机没装 Node 也能跑

VS Code 自带 Electron，可以当 Node 用：

```bash
ELECTRON_RUN_AS_NODE=1 "/c/Users/<你>/AppData/Local/Programs/Microsoft VS Code/Code.exe" tests/run-all.js
```

### 云函数测试是怎么做到不连云的

`tests/mock-wx-server-sdk.js` 是云数据库的内存替身，通过改写
`Module._resolveFilename` 顶掉 `require('wx-server-sdk')`，于是三个云函数能在
本机原样跑。替身里所有异步方法都真的让出一次微任务，`Promise.all` 并发调用时
会在 `await` 点交错——并发报名的竞态才测得出来。

`cloud.test.js` 里还有一个**对照用例**：刻意用"先查后写"的朴素实现跑同样的并发，
断言它**必须超卖**。如果哪天那条对照用例开始通过，说明并发测试已经造不出竞态了，
"不超卖"那条结论也就不可信了。

## 几个需要知道的坑

**免费云环境上线后第 15 天到期。** 小程序未发布前一直免费，**一上线就开始倒计时**。
开发阶段感觉不到，别被突然停服打到。

**不要用 `wx.getUserProfile` 取头像昵称。** 该接口 2022-11-08 已被回收，新版本
只会返回灰色默认头像和"微信用户"。本项目报名表手填姓名，直接绕开了这个问题。

**手机号是用户手动填的**，没有用 `getPhoneNumber`——那个接口要求已认证的
非个人主体小程序，而且按条收费。手机号仅组织者可见（云函数按 openid 分流投影）。

**报名并发控制没有用事务。** 事务对象只有 `doc.get/update/set/remove`，**没有 `where`、
没有聚合**，"还剩几个名额"这类条件查询在事务内做不了；而且默认只重试 3 次，开抢
瞬间大家争同一个 event 文档的锁很容易耗尽。这里用的是 `remaining` 字段 +
条件 `where` + `_.inc(-1)`，看返回的 `stats.updated` 判断是否抢到。

**别在 `exports.main` 外调用 `cloud.getWXContext()`**，模块加载期没有调用上下文。
